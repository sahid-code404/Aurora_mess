    19→## ENVIRONMENT ADAPTATIONS (documented decisions — spec §0 "choose safest behavior + document")
    20→1. Spec asks for NestJS+PostgreSQL+Redis monorepo. Sandbox constraint: single Next.js 16 app on port 3000
    21→   with Prisma/SQLite only. DECISION: implement the spec's DOMAIN MODEL, INVARIANTS, and UX as a
    22→   modular-monolith Next.js app: App Router API routes under `/api/v1/*` act as the REST API layer
    23→   (mirroring the NestJS module boundaries via folder-per-module + domain services in src/lib/domain).
    24→   Redis replaced by in-memory rate limiting. Money stays integer minor units; ledger stays double-entry.
    25→2. Spec asks for `/admin/*` + `/app/*` routes. Sandbox constraint: user can only see `/`.
    26→   DECISION: single-page app at `/` with hash-based routing (e.g. `#/admin/meals`, `#/app/billing`).
    27→   Hash router gives back-button support + shareable state without extra Next.js routes.
    28→3. Spec asks `__Host-session` cookie. Sandbox serves over internal HTTP proxy.
    29→   DECISION: cookie name `mes_session`, HttpOnly, SameSite=Lax, Path=/, 30d expiry. Session tokens are
    30→   256-bit random, only SHA-256 hash stored server-side (spec §10 honored). Documented for prod swap.
    31→4. Spec asks Argon2id. Native module risk in sandbox. DECISION: Node built-in `scrypt` (memory-hard,
    32→   per-user salt, params stored with hash, timingSafeEqual compare). Documented ADR swap for prod.
    33→5. File proofs stored on private filesystem folder `uploads-storage/` (never under public/) with random
    34→   object keys + sha256 checksums + magic-byte validation, served only via authenticated endpoint.
    35→6. Cutoffs/locking are ALWAYS computed from server time (spec §16) — browsers only render countdowns.

   102→### API ENVELOPE (all /api/v1 routes)
   103→Success: `{ ok: true, data: <T>, meta?: { requestId, cursor?, total? } }`
   104→Failure: `{ ok: false, error: { code: "DOMAIN_CODE", message: "plain-language", fields?: {...}, requestId } }`
   105→HTTP status 4xx/5xx. Domain codes used by frontend for friendly copy. requestId = crypto.randomUUID().
   106→
   107→### AUTH
   108→- POST /api/v1/auth/register  { email, password, fullName, phone?, room?, acceptances:[{policyId, policyVersionId}] }
   109→  → user PENDING_APPROVAL (+ status history + policy acceptance rows). Login allowed ONLY when ACTIVE.
   110→- POST /api/v1/auth/login { email, password } → session cookie; generic failure message (no enumeration).
   111→- POST /api/v1/auth/logout. GET /api/v1/auth/me → { user, profile, institution, role }.
   112→- GET /api/v1/auth/policies → active policy versions (public for registration).
   113→- Sessions: token 32B random base64url; store sha256(token); rotation on login; revoke on deactivate.

   115→### ROLE MODEL (ONLY TWO — spec §8)
   116→ADMIN, RESIDENT. Backend guards on EVERY route + ownership checks (resident can only see own data).
   117→Registration → PENDING_APPROVAL → (APPROVE→ACTIVE | REQUEST_CHANGES→CHANGES_REQUESTED | REJECT→REJECTED);
   118→ACTIVE → INACTIVE / PENDING_DELETION. Status history table records every transition w/ reason.

   120→### MONEY (spec §17-18)
   121→All amounts Int paise (`amountMinor`). `lib/money.ts`: fromDecimal/toDecimal (string math), format with
   122→en-IN grouping (₹1,84,320.00), round-half-up ONLY in lib/money.ts. Client shows; server computes.

   124→### MEAL ENGINE (spec §24-33)
   125→- meal_definitions (config) → meal_definition_versions (immutable snapshots) → meal_instances
   126→  (per definition+date, unique) → resident_meals (unique resident+instance).
   127→- Precedence (engine, deterministic): instance missing→NOT_AVAILABLE; membership not active for
   128→  serviceDate→NOT_AVAILABLE; not visible→NOT_AVAILABLE; calendar disableMeals→NOT_AVAILABLE(reason CALENDAR);
   129→  approved leave covering date→ON_LEAVE; deficit policy RESTRICTED→NOT_AVAILABLE(reason POLICY);
   130→  else resident selected state (before cutoff) or baseline default; admin_override_state overrides
   131→  everything for that instance; after cutoffAt → locked for residents; admin override post-lock allowed
   132→  with mandatory reason + audit. effective_state + effective_reason always stored.
   133→- Toggle endpoint: POST /api/v1/meals/:instanceId/toggle { state, expectedVersion } — server-time cutoff
   134→  check inside transaction, optimistic version check (RESOURCE_CHANGED on stale).
   135→- Mid-month join: membershipEffectiveFrom — meals before join cutoff = NOT_AVAILABLE (no retro ON).
   136→- New active resident: defaults applied ONLY to instances with cutoff still in future.

   138→### FINANCE (spec §19-20, 37-44)
   139→- ledger_accounts by code: CASH, RESIDENT_RECEIVABLE, GUEST_INCOME, MESS_EXPENSE, OPERATING_EXPENSE,
   140→  REFUND_PAYABLE (per institution). postJournal({entries:[{accountCode, debitMinor, creditMinor}],
   141→  refType, refId, description}) — verifies SUM(debits)=SUM(credits), never mutates posted journals.
   142→- Payment submit (resident, proof optional file, idempotency key) → PENDING. Admin approve: txn{ lock
   143→  row, verify PENDING, mark APPROVED, post journal Dr CASH / Cr RESIDENT_RECEIVABLE, audit, outbox }.
   144→  Reject/void similar. Refund: checks available credit (funds read model), mode CARRY_FORWARD or
   145→  ISSUE_REFUND w/ journal. Expense (admin) w/ items (server recomputes line totals + total), approve
   146→  posts journal Dr MESS_EXPENSE / Cr CASH; void creates reversal journal (never delete approved).
   147→- Funds read model derives everything from ledger + bills (no mutable balance column).

   149→### FORMULA ENGINE (spec §45-53) — security critical
   150→- Whitelisted variables: total_market_cost, total_guest_income, total_consumed_resident_meals,
   151→  total_guest_meals, total_approved_expenses, resident_consumed_meals, resident_guest_meals.
   152→- Operators: + - * / ( ) SUM MIN MAX ROUND IF. Parser → typed AST (JSON). Evaluator with integer/decimal
   153→  safe math (BigInt/Number paise), divide-by-zero → FORMULA_DIVIDE_BY_ZERO (blocks billing).
   154→- NL mode: POST /api/v1/admin/formulas/parse-nl { text } → LLM (z-ai-web-dev-sdk) returns candidate AST
   155→  JSON → server VALIDATES (whitelist + parse) → preview with current-period numbers → explicit Save.
   156→  NL output NEVER executes without validation. UI always shows "I understood this as: …" preview.
   157→- formula_versions immutable; new version effective from NEXT period by default; applying to OPEN period
   158→  requires impact simulation + explicit confirm; CLOSED/BILLED never recalculated.

   160→### BILLING (spec §52-59)
   161→- billing_periods unique (institution, year, month). OPEN→CLOSING→BILLED (+REOPENED restricted).
   162→- Readiness endpoint runs full checks (payments↔ledger reconcile, expenses↔ledger, no PENDING financials
   163→  required, formula valid, meal duplicates none, instances complete, etc.) → human-readable results.
   164→- Generate: advisory lock (SQLite: transaction serialization + status guard), re-run readiness, snapshot
   165→  ALL inputs to billing_snapshots (JSON + checksum), compute meal charge from active formula version,
   166→  create bills + bill_lines w/ full provenance (qty × unit), adjustments, payments applied, status BILLED.
   167→- Client confirm requires arithmetic answer (e.g. "2 + 9 = [11]") verified server-side.
   168→- Bill numbers: BILL-YYYYMM-NNNN. Corrections on closed periods = adjustments only (bill_adjustments).
