# MASTER IMPLEMENTATION PROMPT — SECURE, HIGH-PERFORMANCE RESIDENT MEAL, FINANCE & OPERATIONS PLATFORM

You are the principal software architect, staff backend engineer, staff frontend engineer, database engineer, security engineer, product designer, QA engineer, and reliability engineer responsible for building this application from scratch.

This is not a prototype.

This is not a UI mockup.

This is not a demo.

Build it as a production-quality application whose priorities, in strict order, are:

1. Data correctness
2. Financial correctness
3. Security
4. Reliability
5. Auditability
6. Maintainability
7. Ease of use for non-technical people
8. Performance
9. Accessibility
10. Visual quality
11. Animation quality
12. Developer experience

Never sacrifice items 1–7 merely to make the UI look impressive.

The finished product should feel like a multi-million-dollar modern Apple-inspired application with a carefully engineered Liquid Glass visual language, but its backend and database must behave like a serious financial/operations system.

Before creating implementation code:

1. Analyze this entire specification.
2. Produce the final module map.
3. Produce the dependency graph.
4. Produce the database schema.
5. Produce important state machines.
6. Produce database invariants.
7. Produce transaction boundaries.

10. Produce design tokens.

12. Produce test strategy.
13. Produce migration strategy.
14. Verify currently supported stable dependency versions.
15. Only then begin implementation.

Do not repeatedly stop for minor design questions.

When a small ambiguity exists:

* choose the safest behavior;

* document the decision;
* preserve historical data.

Never invent major new product modules that were not requested.

# 19. FINANCIAL LEDGER

Implement an immutable double-entry ledger internally.

Residents do NOT need to see accounting terminology.

Backend should maintain:

```text
ledger_accounts
ledger_journals
ledger_entries
```

A journal contains one business transaction.

Entries must balance.

Conceptually:

```text
SUM(debits) = SUM(credits)
```

Posted journals cannot be edited.

A correction creates another journal.

Examples:

Payment:

```text
Dr Cash/Bank
Cr Resident Balance / Receivable
```

Expense:

```text
Dr Expense
Cr Cash/Payable
```

Refund:

```text
Dr Resident Balance Liability
Cr Cash/Bank
```

Exact chart-of-account design should be documented.

# 72. CONCURRENCY

Protect race conditions.

Examples:

Two admins:

```text

```

Only one succeeds.

Two requests:

```text

```

Only one generates.

Resident toggles exactly at cutoff:

backend transaction/server-time check decides.

Use:

* row locks
* optimistic version columns
* unique constraints
* advisory locks
* serializable transactions selectively

Do not use serializable isolation globally without need.

# 101. GLASS MUST NOT BE TOO TRANSPARENT

Critical requirement:

The interface should NOT look like nearly invisible transparent cards.

Content readability is more important than transparency.

Approximate light glass:

```css

backdrop-filter:
  blur(20px–28px)
  saturate(135%–155%);
```

Approximate dark glass:

```css
background: rgba(18, 20, 24, 0.76–0.90);
backdrop-filter:
  blur(20px–28px)
  saturate(130%–150%);
```

Tune per context.

Do not blindly use one opacity everywhere.

# 102. GLASS LAYER CONSTRUCTION

# 103. BLUR PERFORMANCE

# 165. DATABASE CONSTRAINT EXAMPLES

# 167. READ MODELS / KPI PERFORMANCE

Do not calculate giant dashboard aggregations in browser.

Use backend query services.

For critical financial values:

derive from authoritative records.

Never let cache change financial truth.

# 168. CACHE POLICY

Good cache candidates:

* institution appearance settings
* active meal-definition metadata
* static lookup data

Be cautious caching:

* balances
* meal lock state
* payment approval state
* billing readiness

If cached, use extremely clear invalidation and server-authoritative mutation responses.

---

# 169. PERFORMANCE TARGETS

Target strong real-world Web Vitals:

```text

INP < 200ms
CLS < 0.1
```

Interactive feedback should generally begin immediately.

Backend:

simple indexed reads should normally be far below hundreds of milliseconds under normal load.

Track p50/p95/p99.

Do not promise impossible latency over arbitrary networks.
